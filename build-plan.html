Build plan · 4 days

Four Days to a Self-Healing SQL Agent

A day-by-day route from an empty folder to a working agent that writes SQL, runs it against a read-only database, notices when it was wrong, and repairs itself — with a React front end that streams the whole thing as it happens. The build order is chosen so each day teaches one unfamiliar thing at a time.

Python · FastAPI · LangGraph SQLAlchemy · PostgreSQL React · TypeScript · SSE ~7 hrs/day Notebook first, then module
DAY 01 Ground floor Database, ORM, packages, API. One-shot question → SQL → rows.
DAY 02 The loop asyncio, then LangGraph. The one-shot becomes a graph that repairs itself.
DAY 03 Trust & surface Validation the LLM can't talk past, plus the streaming endpoint.
DAY 04 The glass React client that renders each node as it fires, repairs included.
01
Ground floor: data, ORM, packages, API

No AI yet beyond a single prompt at the end. Today is about Python that runs and a database that answers.

Learning goals
01 module routing & packages 02 FastAPI + Pydantic 03 provider routing via env 06 SQLAlchemy engine/session
60 min

Postgres with a real schema and a read-only role

Spin up Postgres, seed customers / orders / order_items / products with enough rows that aggregates are interesting. Create a second login that holds only CONNECT, USAGE, SELECT — then prove it by trying a DELETE as that user and watching it be refused.

why now — the security boundary is a database fact, not a prompt. Establishing it before any LLM code exists means it can never be retrofitted badly.

75 min

SQLAlchemy from the outside in

Notebook 01-sqlalchemy.ipynb: create an engine, watch the connection pool check connections in and out, run Core select() against reflected tables, then define one ORM model over the same table to feel the difference. Reflect the live schema into a description the LLM can read.

learn — engine vs connection vs session lifetime; why pooling exists; when reflection beats hand-written models.

45 min

Turn the notebook into a package

Port to backend/database/connection.py and schema.py. Deliberately break the imports — run the file directly, then as python -m backend.database.schema — and fix them with absolute imports plus a root-level launch.

learn — sys.path, __init__.py, why ModuleNotFoundError depends on where you stood when you typed the command.

75 min

FastAPI: the parts that aren't boilerplate

Stand up GET /api/health and GET /api/schema. Model request and response with Pydantic so /docs becomes usable documentation. Hand the DB session to endpoints through Depends rather than importing a global.

learn — dependency injection as request-scoped resource management; routers to keep main.py from becoming the whole app.

60 min

One LLM interface, several providers

A thin module reading MODEL_PROVIDER, MODEL_NAME, TEMPERATURE from .env and returning a configured chat model. Ask for structured output — {sql, tables_used, reasoning} — as a Pydantic model, not free text. Swap providers by editing .env only, and confirm nothing else changed.

learn — configuration as the seam; structured output as the thing that makes the rest of the pipeline possible.

75 min

Wire the single pass

POST /api/query: question in, schema into the prompt, SQL out, executed on the read-only connection, rows back. No retries, no validation, no graph — a straight line, on purpose.

why bother — this is the baseline the self-healing version has to beat, and by day four you'll want the number.

End of day 1 — checkpoint

A real question (“revenue by region in 2025”) returns real rows through the API. Ask three harder ones and write down which ones failed and why — that list is tomorrow's specification.

02
The loop: asyncio, then LangGraph

The centre of the project. By tonight a query that fails is a query that fixes itself.

Learning goals
04 async / asyncio for real 05 LangGraph state & edges 05 bounded loops
75 min

asyncio, demonstrated rather than described

Notebook 02-async.ipynb: three fake LLM calls sequentially, then under asyncio.gather — time both. Then put a time.sleep inside a coroutine and watch the concurrency vanish. Fix it with asyncio.to_thread.

learn — the event loop is cooperative; one blocking call stalls everything. This is the bug you will otherwise ship on day three.

45 min

Make the stack actually async

Switch to the async LLM client. SQLAlchemy's sync driver stays, wrapped in to_thread so DB work leaves the loop free — noting the async-engine alternative without taking that detour today.

learn — where async def in FastAPI helps, and where it's a lie you tell the framework.

60 min

LangGraph, smallest possible version

Notebook 03-langgraph.ipynb: a TypedDict state, two nodes that each return a partial state update, one edge. Compile it. Print graph.get_graph().draw_ascii() before running anything.

learn — nodes are functions of state returning state deltas; the graph is data you can inspect, which is the entire reason to prefer it over a while loop.

70 min

Port the pipeline into nodes

Define SQLAgentState (question, schema, sql, errors, attempts, result, answer). Rebuild yesterday's straight line as: understand → retrieve schema → generate → execute → respond. Still linear, same output as day one — the shape changed, the behaviour didn't.

learn — a typed shared state as the contract between nodes; why every node stays independently callable.

90 min
The differentiator

Conditional edges and the repair cycle

Add validate, diagnose_error and repair_sql. Route with a conditional edge: valid SQL goes to execution; a failure carries question, SQL, database error and schema into diagnosis, and the repaired query re-enters validation from the top. Bound it with MAX_REPAIR_ATTEMPTS = 3 and a terminal failure state that says what went wrong instead of inventing an answer.

learn — cycles in a graph, the conditional-edge router as a plain function, and why the bound is load-bearing rather than defensive.

45 min

Break it on purpose

Feed the graph a prompt that references a table that doesn't exist. Watch relation "customer" does not exist come back, get diagnosed, get repaired, and succeed on attempt two. Save the rendered graph into the repo as the artefact of the day.

why — a self-healing system you've never seen heal is a claim, not a feature.

End of day 2 — checkpoint

Yesterday's three failing questions now pass, and the state shows how many attempts each took. The graph diagram matches the PRD's picture closely enough to be recognisable.

03
Trust, then the surface it streams through

Half hardening, half API design. Everything today is testable without an LLM in the loop.

Learning goals
02 full API surface 04 async generators 05 streaming graph events
75 min

Three layers of validation, none of them a prompt

Parse with sqlglot for syntax. Walk the parsed tree for table and column names, checking each against the reflected schema — this is what stops hallucinated columns reaching the database. Then the allowlist: SELECT and WITH … SELECT pass, everything else is rejected by default.

learn — static analysis of SQL as an AST rather than a string; allowlist over blocklist, because you can enumerate what's safe but never what isn't.

50 min

The adversarial test file

One test_security.py of pure functions and asserts: stacked statements, a DELETE hidden in a CTE, a comment-smuggled DROP, an UPDATE dressed as a subquery. No LLM, no database, no fixtures — just inputs and expected refusals.

learn — a trust boundary is only real once it's tested in isolation from the thing it doesn't trust.

45 min

Guardrails at execution

Per-session statement_timeout, an enforced row cap, a wall-clock ceiling per request. A query that would scan everything gets cut off rather than served.

learn — timeouts and limits as the last layer, sitting under validation rather than replacing it.

60 min

The rest of the endpoints

POST /api/query returns query_id, sql, status, attempts, rows and answer. GET /api/query/{id} retrieves a finished run from a small store. Errors return structured detail, not a stack trace.

learn — response models as the API contract; exception handlers; why the client shouldn't have to parse prose.

80 min

Streaming: the graph narrates itself

POST /api/query/stream over Server-Sent Events, driven by graph.astream. Each node completion becomes one event — schema_retrieved, sql_generated, validation_failed, repairing, executed. Watch it with curl -N before a front end exists.

learn — async generators end to end, and why SSE is the right size of tool here rather than WebSockets (which day four adds anyway, for the comparison).

End of day 3 — checkpoint

curl -N on the stream endpoint prints the agent's reasoning arriving live, including a repair. The security tests pass, and no prompt is responsible for any of it.

04
The glass: React, streams, and the repair timeline

The backend is frozen from here. Today is entirely about making the invisible visible.

Learning goals
F1 streaming clients F2 custom components F3 AI component libraries
45 min

Vite, TypeScript, Tailwind, and a CORS fight

Scaffold the client, point it at the API, lose twenty minutes to CORS as everyone does, then render /api/schema as a table browser so the user can see what they're allowed to ask about.

learn — typing API responses from the Pydantic models you already wrote; the dev-server proxy.

50 min

Ask a question, see a table

Query box, submit, results grid, generated SQL shown below it. Plain fetch against the non-streaming endpoint first — the boring version, working, before anything streams.

learn — loading and error states as first-class UI, not afterthoughts.

80 min

A hook that consumes the stream

useQueryStream: open the SSE connection, reduce each event into React state, tick off the pipeline as it happens — schema retrieved ✓ · SQL generated ✓ · validated ✓ · executed ✓. Then swap the transport for a WebSocket to feel what changes and what doesn't.

learn — streaming as a state reducer; cleanup on unmount; SSE versus WebSockets with actual experience behind the opinion.

70 min
The money shot

The self-healing timeline

When a repair happens, show it rather than hiding it: attempt one, the SQL, the database's complaint, then attempt two with the corrected SQL diffed against the first. A custom component, built by hand — this is the one view that explains the whole project to someone in five seconds.

learn — designing a component around a data shape you control end to end; why the failure path deserves the best UI in the app.

60 min

Borrow the polish

Bring in shadcn/ui for the shell — dialog, tabs, table, skeletons — plus a token-by-token streamed answer and syntax-highlighted SQL. Use the library for the generic parts and keep the timeline hand-built.

learn — where a component library earns its keep and where it flattens the thing that makes your app yours.

45 min

Demo pass

Run five questions: two easy, two that need joins and aggregation, one engineered to fail and recover. Record it. Note first-attempt accuracy and recovery rate against day one's baseline — the two numbers the whole project exists to move.

learn — evaluation starts as two numbers in a notebook, long before it's a framework.

End of day 4 — checkpoint

A stranger types a question, watches the agent think, sees it stumble and correct itself, and reads the answer — without being told what any of it means.

Done, and deliberately not done

Four days buys a system that demonstrates its own thesis. It does not buy a platform — and the cut list matters as much as the build list.

Shipped
  • ✓Natural language → schema-grounded SQL
  • ✓Read-only execution, enforced at the database
  • ✓Validation independent of the model
  • ✓Automatic diagnosis and repair, bounded at three
  • ✓Inspectable LangGraph, rendered and committed
  • ✓Streaming API and a client that renders each step
  • ✓Baseline vs self-healing, measured on five questions
Cut, and when to add it
  • →pgvector schema retrieval — when the schema stops fitting in a prompt
  • →Multi-turn conversation and checkpointing — day five, once one turn is solid
  • →LangSmith and OpenTelemetry — when a failure gets hard to reproduce
  • →Spider / BIRD benchmarks — after five hand-written cases stop finding bugs
  • →Charts and visualisation — after the table is genuinely not enough
  • →Docker, second database engine, fine-tuning — not this week

If a day runs long, the block to drop is never validation and never the repair loop. Drop the WebSocket comparison, drop shadcn, drop the ORM half of the SQLAlchemy notebook. The project's claim is that the surrounding architecture — not the model — is what makes text-to-SQL reliable, and only two days of this plan actually prove that.
